# 阶段 3 任务说明：账户余额校准

> 交给 Codex 执行。范围严格限制在本文件内，不要碰阶段 0/1/2 已完成的部分。
> 状态：草稿，末尾三个待定项确认后即可开工。

## 1. 为什么要做

阶段 0/1/2 已经把「导入扣余额」补上了，但**只对之后导入的账单生效**。

在 0.4~0.7 期间导入的那批账单，当时是按旧逻辑处理的——流水写进去了，账户余额一分没扣。所以现在磁盘上的余额，和流水能推出来的余额，本来就是两套数。

不修这个问题，前面三个阶段等于白做：`availableBalance`、目标进度、今日可花，全都建立在一个虚高的余额上。

## 2. 目标

给用户一个入口，让他能把「账户余额」一次性校正到真实值，并且**留下审计记录**——知道在哪一刻、调了多少、为什么。

## 3. 为什么不能自动算

看起来可以「按流水反推应有余额」，但缺一个前提：**没有"起始余额"锚点**。

`Account` 只有 `balance`，没有 `balanceAt`。不知道哪个时刻的余额是可信的，反推就没有基点。而账单文件里的"余额"列，历史数据当时也没存下来（只用来做去重键），现在补不回来。

所以唯一可靠的事实源是：**用户打开支付宝/微信/银行 App，看到真实余额，填进来。**

## 4. 设计

### 4.1 入口

设置页（`MyScreen.tsx`）在账户列表下加一项「校准账户余额」。

### 4.2 交互

```
每个账户一行：
  支付宝        记录值 ¥8,000.00
                真实余额 [ 输入框 ]      差额 ¥X（只读，实时计算）
  
底部：[取消]  [确认校准]
```

- 只填需要校准的账户，留空表示不改。
- 差额 = 真实值 − 记录值，实时显示，正负都用红色标出（这是异常信号）。
- 全部留空时「确认校准」置灰。

### 4.3 写入规则（关键）

校准**不能直接改 `balance` 了事**，必须同时生成一笔调整流水：

| 字段 | 值 |
|---|---|
| `type` | 差额 > 0 记 `income`，差额 < 0 记 `expense` |
| `amount` | `Math.abs(差额)` |
| `accountId` | 被校准的账户 |
| `category` | `'余额校准'` |
| `note` | `校准：记录 ¥8,000.00 → 实际 ¥7,200.00` |
| `source` | `'manual'` |
| `occurredAt` | 当前时间 |

理由三条：
1. 钱少了 800，账本上必须有痕迹，否则以后永远说不清钱去哪了；
2. 目标进度、本月支出都要跟着变，直接改余额会让它们悄悄跳变；
3. 出问题时能查——"这笔 800 是 10-18 校准产生的"，而不是凭空蒸发。

一次校准涉及多个账户时，**全部在一个 state 更新里完成**（一次 `commit`），不能一个账户写一次盘。

### 4.4 数据模型

不加新字段。复用现有 `Transaction`。

如果将来要做"自动用账单余额校准"，再考虑给 `Transaction` 加 `balanceAfter?: number`——**这次不做**。

## 5. 边界（明确不做）

- 不改 `derive.ts` / `calculations.ts` 的任何公式。
- 不改导入逻辑（阶段 2 的 `applyImportedTransactions` 保持原样）。
- 不自动推断差额，不静默修正。
- 不做"撤销校准"——校准本身是一条流水，用户可以删掉那条流水，但余额不会自动回滚（这一点要在 UI 上写清楚）。

## 6. 验收

1. 设置页出现「校准账户余额」入口，列出全部非信用账户。
2. 输入真实余额后，差额实时显示，正负都对。
3. 确认后：`account.balance` 变成输入值；同时多出一笔 `category='余额校准'` 的交易。
4. 首页「可用账户」与输入值一致；目标进度按新余额重算。
5. 多账户同时校准时，只产生一次写盘（可以用 codelog 的 change 记录核对，不应出现多条 saveState）。
6. `npm test` 和 `npm run typecheck` 全绿，并新增至少一条测试：校准后余额与流水一致。

## 7. 回滚

- 代码：`git restore` 改动的两个文件即可。
- 数据：校准产生的流水可以直接删除，但**余额不会回滚**——需要再校准一次。这条必须写进 UI 的说明文案。

## 8. 交付格式

按五件事汇报：改了哪些文件、为什么、怎么验证（贴 `npm test` 和 typecheck 原始输出）、怎么回滚、遗留风险。

收尾补一条 codelog summary，`why` 里写清"为什么必须用调整流水而不是直接改余额"。

## 9. 已定项（原三个待拍板）

**① 校准范围：全部账户，含信用账户。** 信用账户按"欠款金额"输入，内部仍用负数存储，输入值和 `balance` 的换算要写清。

**② 差额为 0 的账户不产生流水。** 避免 ¥0 记录污染本月支出统计。

**③ 设置页显示「上次校准：10-18，调整 −¥800」。** 让人一眼分辨余额是校准过的还是系统算出来的。
